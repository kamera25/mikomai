## 1. 目的と基本方針

ネットワーク診断、技術文書検索、機器設定支援という現在の機能を保ちながら、変更箇所を特定しやすく、回帰を検出しやすい構造に整える。まず検証環境と運用上の境界を整え、その後に責務の大きいモジュールを段階的に分割する。

既に `harness` の状態機械、Planner・ToolExecutor・Reporter のポート、承認付き Operation Plan、履歴専用ストア、フェイクを利用するシナリオテストがある。これらを移行の土台として維持する。全面書き換え、別フレームワークへの移行、DB製品の変更、依存関係の一括更新は本計画の初期対象にしない。

優先順序は以下とする。

1. CI・E2E・開発環境の不一致を解消し、改修前の基準を固定する。
2. エージェントの途中終了・再開と外部プロセスの実行条件を明確にする。
3. UI、設定支援、履歴、保存処理を責務ごとに分割する。
4. GUIとCLIの共通処理を整理し、型・エラー・評価手順を統一する。
5. 配布物、依存関係、ナレッジ、設計文書を継続管理できる状態にする。

### 3.3 現在の主要な処理経路

```text
React画面 / Context / Hook
  -> Tauri invoke / イベント購読
  -> MCPリクエスト受付
  -> Dispatcher
       -> Worker（説明、検索、生成等）
       -> AgentLoop（複数段階の観測・判断）
            -> PlannerPort
            -> スキーマ・ポリシー検証
            -> ToolExecutorPort -> MCP -> 機器 / Python / RAG
            -> NetworkState / EventLog
            -> ReporterPort -> UIイベント

変更操作: Operation Plan作成 -> 内容に紐づく承認 -> 実行
CLI chat: Tauriアプリ・非表示ウィンドウを起動 -> 共通チャット処理
```

これは責務の概略であり、すべての実行経路を網羅するコールグラフではない。特にBuilderへの委譲と承認後の実行は、改修前に経路ごとの検証が必要。

## 6. 目標構造と守る契約

### 6.1 目標構造

フロントエンドは「表示」「機能単位の状態管理」「Tauriとの通信」を分離する。既存Contextを維持しつつ、まずチャットイベントの更新ロジックを純粋関数へ抽出する。型付きの通信窓口を設け、画面ごとに散在するコマンド名やエラー処理を徐々に集約する。新しい状態管理ライブラリの導入は前提にしない。

バックエンドは、Tauriコマンド・CLIを入口、チャット・診断・変更計画を共通サービス、状態遷移・承認規則をコア、LLM・DB・Python・UI通知を外部アダプターとして整理する。既存の `PlannerPort`、`ToolExecutorPort`、`ReporterPort` を活かし、必要な範囲で保存・承認の境界を抽出する。全処理を一度にtrait化しない。

### 6.2 変更をまたいで維持する契約

1. 設定変更・ロールバックは、対象と引数が一致する承認済み計画を経由する。
2. 未知ツール、不正引数、拒否・取消・期限切れ等では、意図しない外部変更を起こさない。
3. チャットの最終回答、タスクとイベントの対応、履歴・要約・引用が維持される。
4. 旧保存データを読み込める。形式変更時はバージョンと移行・復元手順を用意する。
5. キャンセル・タイムアウト・外部プロセス失敗は識別でき、UIとCLIへ一貫して通知する。
6. 再開時に結果不明の変更操作を自動で重複実行しない。読み取り操作と変更操作の再試行を分ける。

| Python・配布 | 別作業ディレクトリ、補助実行環境欠落、不正出力、異常終了、タイムアウト、対象OS/CPUでの起動 |
| RAG・LLM | 正しい資料検索、メーカー・機種違い、該当なし、引用と回答の整合、モデル未設定、推論取消 |

実機を変更しないフェイクテストを基本とする。実機での変更操作は、専用の検証機器とレビュー済みの操作計画を使用する。テストの期待値は内部実装ではなく、利用者への結果と不変条件に置く。

### 8.2 実装時の確認コマンド

```bash
# フロントエンドの変更
npm run check
npm run lint
npm test -- --reporter=dot
npm run build

# Rust変更（必要な対象から開始）
cargo test --manifest-path src-tauri/Cargo.toml --lib

# E2Eの設定とモックを整備した後
npm run test:e2e

# コード・設定変更後の必須確認
npm run cli -- chat "F220のVLAN設定方法を教えて"

# RAG変更時（検証用ストアにコーパスを準備した後）
python scripts/rag_eval.py --cases eval/rag_cases.json --report eval/rag-report.json
```

CLIは終了コード0だけでなく、質問に対応した完結した最終回答が出ることを確認する。必要に応じて `--debug` で内部経路を調べる。GUI初期化、モデル、保存先が必要な現在の制約を記録する。`cargo test --lib` は `src-tauri/tests/` の結合テストを含まないため、実効的な結合テストを整備した際はCIの実行対象にも追加する。

### 8.3 成果の測り方

- 型チェック・単体テストの成功を維持し、lint警告5件と `act(...)` 警告の解消、または具体的な残存理由を記録する。
- 承認拒否・途中終了・再開・保存失敗に関するシナリオが、自動テストで再現できる。
- 分割後は、画面変更が機器操作層へ、保存変更が表示層へ不要に波及しないことをレビューする。
- GUI/CLIの最終回答、引用、失敗分類について代表的な依頼の互換性を確認する。
- RAGはR13の指標定義を修正した後に基準結果とRecall@kを比較し、根拠のない回答も別途確認する。現在値未測定のため、数値目標はフェーズ0で設定する。
- 起動時間、初回応答時間、ピークメモリを同一端末・モデル・入力条件で測定する。性能改善の数値は現時点で約束しない。

## 9. 棚卸しでの削除・更新判断

| 区分 | 判断方法 |
| --- | --- |
| Pythonキャッシュ | 生成物であることを確認した追跡済み `.pyc` を追跡解除し、再混入を防ぐignore設定を追加する |
| 複数配置されたバイナリ | Tauriのbundle設定、sidecar起動、ビルドスクリプトの参照を照合し、必要な配置を決定してから整理する |
| 未使用候補の関数・プロンプト・YAML | 静的参照だけでなく、Tauri登録、文字列ディスパッチ、Python・生成物からの参照を調べる |
| JavaScript・Rust依存 | 直接依存の利用箇所、機能フラグ、ロックファイル、OS依存を確認する。更新は領域単位の別変更にする |
| Python依存 | 実際のimportと配布要件を基にバージョン・導入手順・再生成方法を管理する |
| ナレッジ | 出典、対象メーカー・機種、更新日、取込方法、評価ケースとの対応を管理する |
| ローカルキャッシュ・データ | ソース管理の整理と利用者データの削除を分ける。履歴・接続情報・モデル・DBを一括削除しない |

## 10. 移行・レビュー・復旧

1つの変更では、機械的なファイル移動と振る舞いの修正をできる限り分ける。最初に既存の公開APIを保った抽出を行い、その後に呼び出し側を切り替える。新旧の実行経路が残る間は、それぞれの承認と結果記録が同じ規則に従うことを確認する。

保存形式を変更する場合は、履歴、要約、操作計画、イベント、ネットワークDB、RAGごとに旧形式・新形式・移行手順を定義する。検証用コピーとバックアップで移行・復元を確認し、復元できない形式変更を通常のファイル分割に混ぜない。

各変更のレビューには、課題ID、変更する契約、検証結果、保存互換性への影響、戻し方を記載する。コードだけの変更はその変更単位で戻せる構成にし、保存形式変更は事前バックアップの復元手順を伴わせる。

対象OS・CPU、CIに使えるモデル・実行環境、実機検証範囲、旧データの互換性維持期間はフェーズ0で確定する。それまでは既存の対象環境と保存互換性を維持する前提で作業する。
