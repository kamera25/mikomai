## 12. 一から構築する場合の再設計案

### 12.1 結論と前提

一から構築するなら、最初に「GUIなしでチャット・検索・診断を実行でき、変更操作を承認から結果確認まで追跡できるRustコア」を作る。その上にCLIとTauri UIを載せる。ファイル数や行数を減らすことよりも、実行状態の所有者、外部副作用の入口、保存の責任を明確にすることを優先する。

ローカル推論、技術文書の引用、機器の観測、差分確認と承認、日本語UIという現在の要件を前提とする。React・Tauri・Rustの継続利用を設計上の仮置きとし、製品やライブラリの最新版比較は行っていない。DB変更やPython全廃を先に決める根拠は今回の調査にはない。

この章は再構築時の設計提案であり、実装済みの説明ではない。現行製品への適用は段階移行を基本とする。第7章の18〜30人日は旧計画の概算であり、本章の再設計・新規構築の見積もりには流用しない。

### 12.2 現行実装から修正する境界

| ID / 優先度 | 今回確認した根拠 | 一から作る場合の設計判断 | 完了を判断する振る舞い |
| --- | --- | --- | --- |
| G01 / P1 | `cli.rs::run_chat` が `build_app()` を使用。`harness/ports.rs` にポート定義とAppHandle・Windowを持つ本番アダプターが同居 | Tauriを依存に持たないコアとアプリケーションサービスを先に作り、CLI・デスクトップを別の入口にする | ウィンドウ・GUI初期化なしでCLI chatとコアのフェイクテストが動く |
| G02 / P1 | `src/types/index.ts` と `mcp/protocol.rs` に通信型があり、Hookが直接invoke/listenを使用。差分・実行状態に別イベント購読がある | 通信DTOを一元管理し、TypeScript型とテスト用データを生成。境界で入力検証し、UIは型付き通信アダプターを使う | 同じ契約データをRust、UI、E2Eが読み、未知バージョンや不正payloadを明示的に扱う |
| G03 / P1 | AgentLoopの途中保存とEventLogのrenameは実装済み。ただし `persist_event_log` の保存失敗は警告。OperationStoreは別に計画を保存 | タスク・承認・実行記録の整合性を共通サービスで管理し、必要な記録を保存できなければ変更操作を開始しない | 保存失敗時に機器呼出が0回。操作後に記録を失った場合は結果不明として復旧できる |
| G04 / P1 | `operations.rs` に計画ハッシュ、承認、Executingへの遷移がある。Builder等の別経路もある | 変更操作を単一の実行ゲートへ集約。計画の対象・引数・前提条件・版に承認を紐づける | CLI、GUI、Builder、定期実行のどの入口でも未承認変更が通らず、二重実行を拒否する |
| G05 / P2 | `harness/coordinator.rs` に構造化したWorkerOutcomeがある一方、ToolExecutorPortにはツール実行と最終回答生成が同居 | 調整役は状態遷移、ツール実行は観測・操作、回答生成は証拠の説明を担当する | 回答生成の失敗が機器操作の再実行につながらず、記録済みの結果を再表示できる |
| G06 / P2 | `config_python.rs` がcwdからvenvとスクリプトを探索し `wait_with_output` で待つ | Pythonを配布可能なアダプターに閉じ込め、配置・入出力契約・終了期限・キャンセルを統一する | リポジトリやvenvがない配布先、別cwd、異常終了、タイムアウトで期待どおりに動く |
| G07 / P2 | 履歴専用ストア、ネットワークDB、RAG、JSONイベント・計画が存在。`history_store.rs` は初期化時のcheck結果を破棄 | 保存対象を正本と再生成可能なデータに分類し、各々のRepository・形式バージョン・移行責任を定義する | 初期化失敗が伝播し、旧データ移行とバックアップ復元を検証できる |
| G08 / P2 | `mcpListenerState.ts` 等の分割はあるが、`useMcpListeners.ts` は複数イベントの購読と状態更新を扱う | タスク単位の状態更新を純粋なreducerに集約し、購読、描画タイマー、画面表示を分ける | 重複・遅延イベント、履歴切替、再購読でも他タスクの回答や承認状態が混ざらない |

優先度は第5章と同じ定義。G01〜G04は新規構築の骨格とし、後付けの整理に回さない。

### 12.3 依存方向と最小構成

```text
React features ── DesktopClient ── Tauri adapter ─┐
CLI ─────────────────────────── CLI adapter ────┤
Scheduler ─────────────────────────────────────┤
                                               v
                                  Application services
                          Chat / Diagnose / Propose / Approve / Execute
                                               |
                                               v
                                  Domain + port contracts
                          Task / Evidence / OperationPlan / Policy
                                               ^
                                               |
                          LLM / Storage / Device / Python adapters
```

コアはTauri、Window、具体的なDB型、プロセス起動方法を参照しない。入口側の初期化処理がアダプターを組み立てて注入する。Application servicesがユースケースを進行し、Domainは状態遷移と承認規則を保持する。MCPはツール接続の境界として扱い、チャット・保存・UIの内部構造全体をMCPに従属させない。

新規構築時の配置案は次のとおり。最初から全アダプターを別crateにはしない。

```text
mikomai-core/       # domain、application、port。GUI依存なし
crates/mikomai-adapters/   # 推論、保存、機器接続、Python
crates/mikomai-cli/        # 引数・入出力・サービスの組立て
mikomai-desktop/src-tauri/                # デスクトップの組立てとIPC変換
mikomai-desktop/src/features/  # chat、operations、connections、settings
mikomai-desktop/src/platform/  # 型付きIPCクライアント、イベント購読
mikomai-desktop/src/shared/    # 機能に依存しない表示部品
```

現行への移行ではまずモジュール境界を作り、Tauri依存を外せた部分からcrate化する。分散サービス、汎用プラグイン基盤、新しいフロント状態管理ライブラリは必須にしない。追加の運用・抽象化コストを正当化する要件が出た時点で判断する。

### 12.4 実行・承認・復旧を最初に設計する

実行状態の正本はバックエンドが持つ。UIとCLIは同じタスクID・操作IDで状態を取得し、承認や取消をコマンドとして送る。画面を閉じることとタスク取消は別の操作とする。

変更操作は次の順序に固定する。

1. 対象機器、正規化した引数、差分、観測時点の前提条件から変更計画を作成・保存する。
2. 計画のハッシュ・版に対する承認を保存する。計画内容や対象の前提が変われば承認を取り直す。
3. 実行ゲートが承認と前提を確認し、未実行からExecutingへの遷移を競合なく保存する。保存できなければ機器へ送信しない。
4. 機器へ送信し、応答と事後観測を記録する。通信が途切れた場合は、失敗と断定せず結果不明として扱う。
5. 結果不明の操作は観測または人の確認で照合する。変更の自動再送は行わず、再実行が必要なら新しい計画として扱う。

機器側の変更とローカル保存を単一トランザクションにはできないため、内部の冪等性キーだけで「必ず一度だけ実行」を保証しない。Executingのまま復旧した操作も照合対象にする。キャンセルは未送信なら中止、送信後なら結果確認へ移し、停止要求を変更の取り消し成功として表示しない。ロールバックも独立した承認付き変更として扱う。

TaskRepositoryとOperationRepositoryの整合性が必要な更新は共通のトランザクション境界で扱う案を第一候補とする。別保存先を維持する場合は、再起動時の照合規則を先に定義する。UI通知は保存済みの状態から再取得可能にし、イベントにtaskId・連番・形式バージョンを持たせる。欠落時はスナップショット取得、重複時は同じ連番を無視する。全領域のイベントソーシング化までは要求しない。

### 12.5 推論・検索・データの扱い

- **推論**: モデルのロード・解放、同時実行数、待ち行列、キャンセルは推論アダプターが管理する。LLMは候補の提案と説明を担当し、実行権限と引数検証は通常コードで確定する。
- **回答**: 観測結果・引用・実行状態を構造化したEvidenceとして回答生成へ渡す。文章化が失敗しても操作の成否は失わず、記録済みの結果を定型表示できるようにする。
- **RAG**: 取込・検索・回答生成を分離する。文書ID、出典、メーカー・機種、文書版、チャンクID、埋め込みモデルと取込版を記録する。機種の不一致や根拠不足を評価ケースに含め、Recall@kと回答の根拠整合性を分けて測る。
- **保存**: 履歴、計画、操作記録、利用者設定を正本として保護する。検索インデックスや要約は原文と生成条件から再生成可能かを確認する。観測データには取得時刻と出所を持たせ、古い観測を現在状態と混同しない。
- **資格情報**: コアには秘密値ではなく参照IDを渡し、接続アダプターで解決する設計とする。イベント、モデルへの入力、デバッグ出力、評価データへ秘密値を持ち込まない。この記述は設計要件であり、現行の漏えいを確認したものではない。

SurrealDBを維持するかは、必要なトランザクション、検索、グラフ問い合わせ、バックアップ、配布容量を代表データで検証して決める。先に保存契約を作り、製品置換と責務整理を同じ変更に混ぜない。Pythonも機器接続資産を再利用し、純粋な変換処理のRust移植は配布負荷と検証工数を比較して個別に判断する。

### 12.6 新規構築の順序と現行への適用

| 段階 | 新規構築なら最初に作るもの | 現行からの移行方法 | 完了条件 |
| --- | --- | --- | --- |
| A: 実行の骨格 | GUIなしのCLI、Task、Evidence、フェイク推論・ツール・保存 | 既存harnessのポート定義と本番アダプターを分離し、チャットサービスを抽出 | 同じ入力に対する成功・失敗・取消をモデルや機器なしで再現できる |
| B: 読み取りの縦断経路 | 文書検索→証拠→最終回答、診断→観測→回答 | CLI chatから共通サービスを呼び、既存GUIは互換アダプターで接続 | GUIとCLIが同じ主要結果・引用・失敗分類を返す。実モデルで最終回答を確認する |
| C: 変更と復旧 | 計画、承認、実行ゲート、永続化、結果不明からの照合 | OperationStoreとAgentLoopの保存境界を整理し、各変更経路をゲートへ接続 | 同時実行、承認不一致、送信前後の中断、保存失敗で意図しない変更が起きない |
| D: GUIと配布 | 共通契約を使うUI、Pythonアダプター、対象環境のビルド | 型付き通信へ機能単位で切替え、配布先パス解決を統一 | UIの重複・欠落イベント回復と、クリーンな配布先での起動を確認できる |
| E: 運用機能 | 履歴移行、監査、定期実行、評価と性能測定 | 既存機能を同じサービスへ順次接続し、旧経路を削除 | バックアップ復元、旧データ移行、定期実行の承認規則を検証できる |

既存の状態機械、Coordinator、承認ハッシュ、履歴ストア、フェイクシナリオ、分割済みUI部品は再利用する。新旧経路を比較する場合、変更操作はフェイクで比較し、実機へ二重送信しない。各段階で公開契約と保存互換性を確認してから旧経路を廃止する。

直近の実装単位は **G01のチャットサービス抽出とCLIのGUI依存除去** とする。先に必要なAppHandle由来の依存（設定、保存先、モデル、通知、対話待ち）を一覧化し、移す責任を確定する。並行して未修正のR06は独立した小変更で扱える。その後G03・G04の保存・実行契約、G02・G08のUI契約へ進む。全面再構築に進む判断は、Bまでの試作結果と互換性維持の費用を確認してから行う。

### 12.7 検証と未決事項

通常のCIは、コアのフェイクテスト、通信契約、フロントの型・lint・単体テストを対象とする。実モデル評価、実機検証、対象OS・CPUでの配布確認は別の検証段階として結果を記録する。コード変更後は既存ルールどおり `npm run cli -- chat "F220のVLAN設定方法を教えて"` を実行し、完結した最終回答まで確認する。新しいヘッドレスCLIが完成するまでは現行CLIでも検証を継続する。

着手時に確定する事項は、配布対象OS・CPU、同時タスク数、機器単位の排他制御、履歴と監査の保存期間、承認期限、旧データの互換期間である。性能目標は同一モデル・端末・質問で起動時間、初回応答、メモリ、検索品質の基準を取ってから設定する。

今回の更新は主要経路の静的再確認と文書編集のみ。第4章の検証結果は初期調査の記録であり、今回再実行した結果ではない。アプリケーションコード・設定・依存関係の変更がないため、CLI chatを含む動作テストは実行していない。

## 13. 再構築実施計画（2026-09 承認済み）

第12章の設計思想に基づき、一から再構築することを前提とした詳細実行計画を策定し、以下の重要方針について意思決定・承認を完了した。

### 13.1 確定した基本方針（決定事項）

1. **SurrealDB 3.1.0 の維持**:
   - 保存層は `PersistencePort` / `GraphStorePort` で抽象化し、アダプター内に直接依存を封じ込める。当面は SurrealDB 3.1.0 を維持する。
2. **Python処理のRust再実装**:
   - `config_python.rs` 経由のCisco設定変換・nwdiag生成等のPython処理は、配布負荷低減と安定性向上のため段階的にRustで再実装し、Python依存を解消する。
3. **TypeScript DTO自動生成**:
   - Rust型から `ts-rs` によるTypeScript DTO自動生成は、Phase 4（フロントエンド再構築）の段階で導入する。
4. **既存crateスケルトンの置換**:
   - `mikomai-core` のスケルトン型は、`mikomai-desktop/src-tauri/src/` の実績ある実装（`OperationPlan`, `AgentLoop` 等）をcoreへ移植して置換・実体化する。
5. **段階的実行ロードマップ**:
   - Phase 0（ベースライン固定・棚卸し: 2〜3人日）→ Phase 1（コアcrate実体化: 5〜8人日）→ Phase 2（アダプター・ヘッドレスCLI: 5〜7人日）を第一段階（計12〜18人日）として最優先で遂行する。

### 13.2 フェーズ別マイルストーン

- **Phase 0: ベースライン固定・棚卸し**
  - E2Eポート不一致（R02）修正、ESLint警告分類、全80+ invokeハンドラ・イベント・保存パスのインベントリ一覧作成。
- **Phase 1: コアcrate実体化 (`mikomai-core`)**
  - Tauri非依存のドメインモデル移植、ポート定義、Application Services（Chat/Diagnose/Operations）の構築、完全インメモリ・フェイクアダプターでのテスト確立。
- **Phase 2: アダプター実装とヘッドレスCLI (`crates/mikomai-adapters`, `crates/mikomai-cli`)**
  - SurrealDB/ファイル保存アダプター、LLM推論アダプター、MCPツールアダプター、Python設定変換のRust移植着手、GUI不要の真のヘッドレスCLI (`mikomai-cli`) 実装。
- **Phase 3: デスクトップ薄層化 (`mikomai-desktop/src-tauri`)**
  - 80+ invokeハンドラを5ドメインサービスへ集約、Tauriを薄いIPC変換層へ純化。
- **Phase 4: フロントエンド再構築 (`src/`)**
  - 型付きIPCクライアント、`chatReducer` による状態純粋関数化、責務分離（`useMcpListeners` 解体、UI部品リファクタリング）。
- **Phase 5: 配布・品質保証**
  - CIパイプライン刷新、クリーン環境ビルド検証、ドキュメント同期。
