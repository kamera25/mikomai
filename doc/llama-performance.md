# llama.cpp バックエンドの速度改善

Apple Silicon の macOS では、GPU offload 対応ビルドならモデルの全レイヤーを GPU に載せる設定を既定とする。その他の環境の既定値は CPU。`MIKOMAI_N_GPU_LAYERS=0` で CPU のみ、正の整数で offload するレイヤー数を指定できる。不正な値は読み込みエラーになる。モデルの読み込み後に変更した場合は再読み込みが必要。

Rust バインディングは `llama-cpp-2` / `llama-cpp-sys-2` の `0.1.159` を使用する。バインディングに同梱される llama.cpp は upstream の最新リリースとは限らない。

KV の型は F16 とする。Q4_0 の再利用では今回の実モデルで回答の言い回しに差が出たため、精度と Metal の速度を優先して F16 を使用する。これはモデル本体の GGUF 量子化とは別の設定であり、すべての入力で文章の完全一致を保証するものではない。

モデルと推論コンテキストは専用スレッドで保持する。通常テキスト生成と grammar 制約付き生成に各1個のコンテキストを保持し、リクエスト間で入力トークン列の共通先頭部分だけを KV キャッシュから再利用する。変更箇所以降の古い入力・生成トークンは削除する。入力が完全一致する場合でも最後の入力トークンを再評価し、今回の入力の logits を取得する。部分削除非対応のモデルは全消去して再評価する。

モデル再読み込み、コンテキスト長変更、推論エラー、キャンセル時には該当するキャッシュを破棄する。温度・生成上限・ペナルティ・grammar の sampler は毎回作成する。Vision はテキストの KV キャッシュを再利用しない。保持するキャッシュはメモリ上だけで、ディスクには保存しない。最大2個のテキストコンテキストを保持するため、従来より待機中のメモリ使用量が増える。Gemma 4 E4B の今回の実測では、8192トークンの F16 KV バッファは1コンテキストで448 MiB（別途作業バッファが必要）。終了時には推論スレッドでコンテキスト・モデル・バックエンドを解放し、Metal の終了処理に先行させる。ストリーミングの callback は呼び出し元スレッドで実行する。

`MIKOMAI_DISABLE_KV_CACHE=1` を設定すると、比較計測のために毎回コンテキストを作成して入力を全評価する。`--debug` の stderr にはコンテキスト再利用、入力・再利用・評価トークン数、最初の生成トークンまでの時間と推論全体の時間を出力する。モデル読み込みとリクエスト待ち時間はこの時間に含まない。

## 実モデル検証

```bash
cargo run -p mikomai-llm-llamacpp --example performance -- /absolute/path/model.gguf
cargo run -p mikomai-llm-llamacpp --example performance -- /absolute/path/model.gguf cpu
```

GPU モードでは同じプロセス内でキャッシュなし・ありの回答一致、入力末尾変更、grammar 用途との分離、エラー・キャンセル後の再作成、ストリーミング、コンテキスト長変更、モデル再読み込みを確認する。CPU モードはCPU指定と同一入力での回答一致・速度比較を確認する。greedy sampling、2048トークンのコンテキスト、32生成トークン上限で測定する。この短い入力での速度差を、長い資料・異なるモデル・エージェント全体の速度差として扱わない。


## 2026-10-10 の実測

環境: Apple M4、24 GiB RAM、Gemma 4 E4B `gemma-4-E4B-it-UD-Q4_K_XL.gguf`、F16 KV、`llama-cpp-2` / `llama-cpp-sys-2` 0.1.159。ビルドは Rust dev profile、native llama.cpp は既定の Release。GPU は43/43レイヤーの offload を確認した。モデル読み込みと初期化時間を除く。

入力:「VLANとは何ですか。日本語で簡潔に説明してください。」。187入力トークン、2048トークンのコンテキスト、生成32トークン上限、temperature=0。キャッシュなし2回、同一入力キャッシュあり3回の平均。CPUとGPUの計測プロセスは順に実行した。

| 実行条件 | 最初の生成トークンまで | 推論全体 |
| --- | ---: | ---: |
| CPU・キャッシュなし | 4197.79 ms | 6555.26 ms |
| CPU・同一入力キャッシュあり | 69.25 ms | 2322.53 ms |
| GPU・キャッシュなし | 672.77 ms | 1877.81 ms |
| GPU・同一入力キャッシュあり | 73.26 ms | 1277.91 ms |

GPU の同一入力では186/187入力トークンを再利用した。入力末尾を日本語から英語に変更した場合は174トークンを再利用、13トークンを評価し、回答開始まで173.00 ms（同じ英語入力のキャッシュなし:863.21 ms）。各バックエンド内で、これらのキャッシュあり・なしの回答は今回の入力で完全一致した。

これは同一モデル・短い入力の比較であり、0.1.156 と0.1.159の更新単独の効果を分離した計測ではない。実際の会話では共通先頭部分の長さで効果が変わる。RAG検索・イベント保存・UI描画の時間は別途加わる。

- CPU指定の実モデル検証:CPUバッファ利用、同一入力の回答一致、キャッシュ再利用が合格。終了コード0。
